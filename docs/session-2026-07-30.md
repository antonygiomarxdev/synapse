## Bugs Found & Fixed

### Bug 1: RoPE Theta (FIXED)

**Symptom:** Logits completely wrong after attention layers.

**Root cause:** `rope_theta` was hardcoded to `10000.0` in `rope_inplace()`. Model uses `10^7` (10,000,000).

**Fix:** Pass `model.config.rope_theta` to `rope_inplace()` instead of hardcoding.

**Evidence:**
```
granitemoe.rope.freq_base: [1.e+07]
```

**Location:** `forward.rs:348` — `rope_inplace()` function

### Bug 2: Embedding Stride (FIXED)

**Symptom:** Embedding values wrong for tokens beyond first dimension.

**Root cause:** Q8_0 dequantization produces 75,502,080 elements, but tensor shape is [1536, 49155] = 75,505,920. Difference of 3,840 elements (120 Q8_0 blocks). The actual stride is 49120, not 49155.

**Fix:** Use `actual_vocab = embd.data.len() / d` instead of `shape[1]` for stride.

**Evidence:**
```
token_embd shape: [1536, 49155], total elems: 75502080
75502080 / 1536 = 49120 (actual stride)
```

**Location:** `forward.rs:34-41` — embedding lookup, `forward.rs:135-148` — logit computation

### Bug 3: Granite Scaling Factors (FIXED)

**Symptom:** Logits ~48x too large for single token, ~2.4x too large for full forward.

**Root cause:** Granite MoE uses scaling factors not present in standard transformers:
- `embedding_scale = 12.0` — applied to embedding lookup
- `residual_scale = 0.22` — applied to attention and FFN outputs before residual
- `logit_scale = 6.0` — applied to final logits (division)

**Fix:** Load from GGUF metadata and apply in forward pass.

**Evidence:**
```
granitemoe.embedding_scale: [12.]
granitemoe.residual_scale: [0.22]
granitemoe.logit_scale: [6.]
```

**Key detail:** In llama.cpp, `residual_scale` is applied to the attention/FFN output BEFORE adding residual:
```cpp
// llama.cpp granite-hybrid.cpp:237-240
cur = ggml_scale(ctx0, cur, hparams.f_residual_scale);
ffn_inp = ggml_add(ctx0, cur, inpSA);
```

**Location:** `model.rs:145-152` — config loading, `forward.rs:44,78,112,147` — application

## What Was Tried But Didn't Work

### Attempt 1: Column-Major mat_vec

**Hypothesis:** GGML stores tensors in column-major order, so mat_vec should use `data[c * rows + r]` instead of `data[r * cols + c]`.

**Result:** Logits changed slightly but correlation with reference remained ~0.

**Conclusion:** GGML uses row-major order (ne[0] varies fastest). The stride documentation was confusing but the original implementation was correct.

### Attempt 2: mat_vec_transposed

**Hypothesis:** `ggml_mul_mat(a, b)` computes `a^T @ b`, not `a @ b`. Need to transpose the multiplication.

**Result:** Logits didn't change after recompile. The function signature was updated but the computation might have been equivalent for square matrices.

**Conclusion:** Need to verify this more carefully. The ggml_mul_mat documentation says result shape is `[a->ne[1], b->ne[1]]`, which suggests transposed multiplication.

## Root Cause Hypothesis (Unverified)

The attention computation is not working correctly. Possible causes:

1. **Q/K/V projection transposition:** `ggml_mul_mat(a, b)` might compute `a^T @ b` (not `a @ b`). Our mat_vec might need to be transposed.

2. **Expert FFN weight indexing:** 3D tensors [d_model, d_ff, n_experts] might have different stride than assumed.

3. **RoPE application:** Position encoding might be applied to wrong dimensions or with wrong formula.

4. **Softmax scaling:** Attention scores might be scaled incorrectly before/after softmax.
